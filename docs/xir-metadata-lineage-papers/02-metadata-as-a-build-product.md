# Metadata as a Build Product

## Abstract

Metadata is often treated as information that must be copied into, curated inside and synchronized with a central metadata platform. An alternative is to produce technical metadata from the authoritative engineering artifacts during the normal software build and delivery process. Source code, configuration, schemas and architecture models remain authoritative for the facts they originate. Deterministic transformations derive call graphs, table usage, lineage and component models. These derived artifacts can be published quickly to a governed metadata authority such as Collibra without making the catalog responsible for discovering every implementation fact itself.

## 1. The problem is metadata propagation

A statement such as "Collibra is the metadata authority" is useful only if implementation changes propagate to that authority quickly and reliably.

The operational requirement is therefore:

> A relevant code or configuration change must cause the corresponding metadata change automatically and within a known time bound.

This changes the focus from metadata storage to metadata production.

```text
code change
   ↓
build / CI
   ↓
parse and observe
   ↓
derive metadata
   ↓
bind and stitch
   ↓
publish
   ↓
metadata authority
```

## 2. Authority stays close to evidence

Different systems can be authoritative for different facts:

```text
source code      -> implementation
configuration    -> deployment and bindings
ArchiMate        -> intended architecture
database catalog -> physical data structures
```

A central catalog can still be authoritative for the governed enterprise metadata view. This does not require it to be the original source of every fact it publishes.

A useful distinction is:

- **evidence authority**: where a fact originates;
- **derivation**: how an assertion is reproducibly calculated;
- **publication authority**: where the governed enterprise view is exposed.

## 3. Do not maintain what can be derived

Call trees, procedure-to-table maps and technical lineage are examples of information that can often be calculated from implementation evidence.

Instead of maintaining them separately:

```text
source + derivation rules -> generated metadata
```

The generated result is disposable in the same sense as a compiled artifact. If the source or rules change, rebuild it.

This gives a simple communication principle:

> Treat metadata as a build product.

The implementation may use functional programming, XSLT and immutable trees, but those are mechanisms rather than the message.

## 4. Why functional derivation helps

A traditional analysis implementation can accumulate state:

```text
parse procedure
-> update symbol table
-> update call graph
-> update table map
-> resolve references
-> mutate repository
```

A functional pipeline instead derives values:

```text
calls(XIR)  -> call map
tables(XIR) -> table map
component(XIR, call map, table map) -> component XIR
```

The benefit is not ideological purity. It is engineering control:

```text
same evidence + same derivation rules = same result
```

This reduces classes of defects involving stale state, partial updates, processing order, shared mutable data and inconsistent intermediate repositories. It does not eliminate logical errors in the derivation rules.

## 5. A vertically coherent metadata chain

A useful enterprise view starts above source code.

```text
ArchiMate
   ↓
Application Component
   ↓
metadata binding
   ↓
configuration
   ↓
implementation artifacts
   ↓
parsed observations
   ↓
derived knowledge
   ├─ calls
   ├─ table usage
   ├─ transformations
   ├─ dependencies
   └─ lineage
```

The important operation is **binding**. Architecture, configuration and code are not collapsed into one model. They are treated as different observations of the same system and connected through evidence-backed relationships.

## 6. Metadata production versus metadata cataloging

A catalog is good at governance, publication, search, stewardship and consumption. Those capabilities do not remove the need for upstream production of high-quality metadata.

The production problem asks:

- Where did this assertion originate?
- Can it be reproduced?
- Which source revision produced it?
- Which derivation version produced it?
- How quickly did it reach the governed metadata view?

This makes **metadata propagation latency** an explicit quality characteristic.

```text
metadata latency = publication time - source change time
```

For metadata generated by CI/CD, an appropriate target is the same delivery cycle that introduced the implementation change, rather than a later manual harvesting exercise.

## 7. Provenance is part of the assertion

A derived relationship should carry enough information to defend and reproduce it.

Example XIR:

```xir
(relation
  {type "READS"
   subject "procedure:B"
   object "table:TABLE_X"
   source-revision "abc123"
   derivation "plsql-table-access/1.4.0"
   evidence "source-span:421-438"})
```

The graph edge is therefore not simply `B READS TABLE_X`. It is an assertion with provenance.

## Conclusion

The metadata authority does not have to perform all metadata discovery itself. A stronger architecture lets implementation and architecture sources remain authoritative for the facts they originate, derives technical knowledge deterministically, and propagates the resulting assertions into the governed metadata authority as part of delivery.

The practical principle is simple:

> Do not manually synchronize metadata that can be rebuilt from authoritative evidence.
